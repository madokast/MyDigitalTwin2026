# MyDigitalTwin2026 MCP

MyDigitalTwin2026 是 mdk 的个人数字孪生。你已经通过 MCP 连上它。它保存 mdk 的真实发言、客观上下文、AI 分析和标签，并提供历史查询与当前时间。

它不会自己记账：你读历史、你在聊天时写入，记忆才会更新。每次新会话，先读长期历史和近期状态，再结合当前时间和眼前对话建立临时上下文，从而更准确地理解他的背景、兴趣、习惯、近期生活和持续关注的问题。

它不规定你的人格或聊天风格，而是一份独立的个人记忆与上下文。工具名、参数和回包以客户端里的工具列表为准；本文只说新建聊天时怎么建立上下文，聊天过程中怎么记、怎么聊，以及回顾和代办这类特化场景。

## 新建聊天：初始化 mdk 上下文

每次新建聊天，按下面顺序初始化上下文。

### 第一步：读取最早的 200 条记录

用 `records_query` 取第一页。`records` 按 id 升序，所以第一页是最早的一批。初始化时显式传 `page_size: 200`，不要用默认页大小。建上下文时的查询都不要带筛选，只要页码和页大小。

```json
{"page": 1, "page_size": 200}
```

综合这些记录的 `raw_content`、`objective_context`、`ai_analysis` 和 `tags`，建立对 mdk 长期情况的初步认识。

重点了解：

* mdk 的基本背景与长期特征
* 兴趣、习惯与偏好
* 工作、学习、生活等长期状态
* mdk 过去反复出现的问题
* mdk 与 AI 的长期交流特点
* 其他对后续聊天具有持续参考价值的信息

基于这些记录，在**当前会话内部**形成一份 mdk 画像。

不要把画像写回 MyDigitalTwin2026，除非 mdk 明确要求记录。

### 第二步：读取最近的记录

看第一步回包里的整数 `total` 和 `total_page`，按下面分支选路。不要把占位词当成参数原样提交，也不要传 `page: 0` 或 `page_size: 0`。

- `total` 为 0：不要再查。长期和近期都记为「尚无记录」，去做第三步。
- `total` 不超过 200（第一步已经拿全）：不要再查，也不要算 `total_page - 1`。这一批同时当长期和近期。
- `total` 在 201～599：再查一次，把 `page_size` 设成这个 `total`。例如 `total` 为 400：

```json
{"page": 1, "page_size": 400}
```

- `total` 不少于 600：每页 200，只取最后两页。例如 `total` 为 900、`total_page` 为 5，则取第 4 页和第 5 页：

```json
{"page": 4, "page_size": 200}
{"page": 5, "page_size": 200}
```

综合这些记录，重点了解 mdk **近期生活状态**：

* 最近正在做什么
* 最近关注什么问题
* 最近的工作、学习和生活状态
* 最近发生的重要事件
* 最近形成或改变的计划
* 最近持续讨论的话题
* 最近的情绪、行为和生活节奏变化

形成一份「mdk 最新生活情况」的临时上下文。

### 第三步：读取当前时间

调用 `time`，取得当前日期、时间、星期和时区。

结合 mdk 长期画像、近期生活情况以及当前时间，推断 mdk 此刻可能处于什么生活场景。

例如：

* 工作日晚上 → 可能已经下班，进入休息时间
* 深夜 → 可能准备睡觉
* 工作日上午 → 可能正在工作或学习
* 周末下午 → 可能处于休闲、外出或个人事务时间

这种推断只当回复上下文，**不得当成确定事实**。

### 第四步：开始聊天

眼前这句话也算 mdk 的一条发言。初始化完成后，若他已经开口：先按下一节写入，再开场；写入失败仍要开场。还没有开口，就直接开场。

综合长期画像、近期情况、当前时间和眼前这句话，生成开场白。

```text
mdk 长期画像
        ↓
mdk 近期生活情况
        ↓
当前日期 / 时间 / 星期
        ↓
当前聊天内容
        ↓
生成个性化回复
```

开场白要自然，不要机械复述画像。

例如时间、近期记录和历史都指向「刚收工」，可以从当前状态切入，而不要说：

> 「根据我的数据库，你今天应该已经下班了。」

## 聊天过程中：实时记录 mdk 发言

mdk **每发一条消息**，先分析，再调用 `records_post` 写入，然后再回复。

其中：

* `raw_content`：mdk 当前消息，**必须原封不动保存**
* `objective_context`：这条消息的客观上下文
* `ai_analysis`：你对这条消息的分析
* `tags`：按内容加适当标签

例如 mdk 说：

```text
今天终于把那个项目收尾了，累死我了
```

可以记录为：

```json
{
  "raw_content": "今天终于把那个项目收尾了，累死我了",
  "objective_context": "mdk 表示今天完成了一个项目的收尾工作，并表达了明显的疲劳感。",
  "ai_analysis": "mdk 当前可能处于项目完成后的放松阶段；后续回复可以关注其休息状态，但不应过度解读其情绪。",
  "tags": ["工作", "项目", "休息"]
}
```

**记录失败不应阻塞聊天。** 写入暂时失败时继续回答，不要因此中断对话。

开场读过的那几页不是全部记忆。聊天里要核对某段历史时，再调用 `records_query` 去搜，不要只靠初始化时读过的内容硬答。

## 聊天风格

MyDigitalTwin2026 **不规定具体聊天风格、语气、人格或回答方式**。

怎么聊，由 mdk 在当前 AI 里的设定决定。

这里只做三件事：

```text
提供 mdk 历史信息
        +
持续记录 mdk 当前信息
        +
提供当前时间
        ↓
帮助你更准确地理解 mdk
```

不要因此扮演必须温柔、严肃、活泼、专业、像朋友、像秘书或像心理咨询师。具体行为由系统提示词、mdk 设置和当前对话决定。

## 联网搜索

可以根据当前消息和上下文，**适当搜索与话题相关的最新信息**。

例如 mdk 正在讨论：

* 最新科技新闻
* 软件版本
* 当前产品价格
* 历史事件的最新研究
* 当地商家
* 体育比赛
* 政策或时事
* 当前网络服务状态

搜到之后，再叠上 mdk 的历史兴趣和近期状态来回答。目的不是堆搜索结果，而是：

```text
mdk 当前问题
    +
mdk 长期兴趣
    +
mdk 近期状态
    +
最新外部信息
    ↓
更加个性化的回答
```

是否搜、搜什么、怎么用，由你根据对话自己决定。

## 整体工作流程

```text
新建聊天
   │
   ├── records_query  page=1, page_size=200（不要带筛选）
   │       ↓
   │   建立长期 mdk 画像
   │
   ├── 若 total = 0：不再查，记为尚无记录
   │   若 total ≤ 200：不再查，第一步那批同时当近期
   │   若 201 ≤ total ≤ 599：再查 page=1, page_size=total
   │   若 total ≥ 600：再查最后两页（每页 200）
   │       ↓
   │   分析 mdk 近期生活情况
   │
   ├── time
   │       ↓
   │   获取当前时间
   │
   └── 若 mdk 已经说了第一句
   │       先 records_post（失败也继续）
   │   综合以上信息
           ↓
       个性化开场白
           ↓
       开始聊天
           │
           ▼
    mdk 发送一条消息
           │
           ├── 分析消息
           │
           ├── records_post
           │
           ├── 需要核对历史时再 records_query
           │
           ├── 回顾 / 代办见「特化场景」（仍先记录，再查询或扭转）
           │
           ├── 根据需要搜索外部信息
           │
           └── 生成回复
           │
           ▼
       mdk 继续聊天
           │
           └────── 循环
```

## 特化场景

以下两条补充前面的用法，不替代它们。回顾或代办时，仍先 `records_post` 记下当前发言；需要历史时再 `records_query`。

### 每日回顾/复盘

mdk 进行每日回顾/复盘时，以对话指向的复盘日期为 X。先写入这条发言，再搜索 X、X+1 两天的记录，因为有些 X 日的事件会被追叙在 X+1 日中。

用 `records_query` 按 `created_at` 过滤：`from` 含、`to` 不含。日期可用 `YYYY-MM-DD`（当天 00:00 +08:00）。例如 X 为 `2026-08-25`，要覆盖 25 日与 26 日，`to` 取 X+2：

```json
{"from": "2026-08-25", "to": "2026-08-27"}
```

若 `total_page` 大于 1，继续翻页取完。

根据搜到的记录，筛选其中确实发生在 X 日的事件，深入分析，输出 X 日的timeline，以及值得 mdk 进一步深入探讨的一些要点。

### 代办（用三个 tag 模拟）

系统通过 `任务-代办`、`任务-完成`、`任务-终止` 三个 tags 模拟代办任务。`任务-代办` 表示该记录是一条未完成的代办；将其扭转为 `任务-完成` 表示代办任务完成；扭转为 `任务-终止` 表示代办任务终止。

扭转请采用**单记录 tag 重命名**：调用 `records_tags_rename`，参数 `tag` → `new_tag`，只改这一条记录，不是全库改名。使用 `records_query` 可以快速搜索各类代办任务；过滤字段是 `tag`（数组，须全部命中；记录字段是 `tags`）：

```json
{"tag": ["任务-代办"]}
```

`任务-完成`、`任务-终止` 同理。

当 mdk 对话涉及代办任务时，请**仍先记录对话内容，然后再创建或扭转代办任务**。先 `records_post` 记下当前发言，再按情况做下列之一：

- 创建：对刚写入的那条记录调用 `records_tags_attach`（`record_id` 用回包的 `record.id`，`tag` 为 `任务-代办`）。
- 扭转完成：查到目标代办任务后，对该记录调用 `records_tags_rename`：

```json
{"record_id": 2504, "tag": "任务-代办", "new_tag": "任务-完成"}
```

- 扭转终止：同上，`new_tag` 为 `任务-终止`。

扭转改的是那条代办任务记录，不是刚写入的对话记录。
